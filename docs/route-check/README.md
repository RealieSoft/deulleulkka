# 우회 시간 어림 비교 (공개 길찾기 경로 20건)

들를까는 경유지를 넣기 전에 "들르면 얼마나 더 걸리는지" 어림해 묻습니다. 그 어림을 공개 길찾기 엔진의 경로 값과 비교했습니다.

- 길찾기: OSRM 공개 데모 서버(`router.project-osrm.org`). 교통 정보가 없는 값입니다.
- 지도 자료: © OpenStreetMap contributors (https://www.openstreetmap.org/copyright). `raw/`에는 OSRM이 OpenStreetMap 자료로 계산해 돌려준 응답을 받은 그대로 두었습니다. `raw/`는 팀의 저작물이 아니라 ODbL(Open Database License)을 따르는 OpenStreetMap 자료입니다.
- 한 경우는 지금 위치 A, 찜 P, 목적지 B로 이뤄집니다. A는 출발지에서 B로 가는 경로를 따라가다 P에서 직선 1.9km 안에 처음 들어온 지점입니다(앱의 찜 반경 2km 진입 직후).
- 실제 추가 시간 = (A→P→B 경로 시간) − (A→B 경로 시간)

## 비교한 식

| 식 | 내용 |
|---|---|
| V0 (처음 엔진) | (d(A,P) + d(P,B) − d(A,B)) × 1.3 ÷ 평균 속도. d는 직선거리, 평균 속도는 남은 거리 ÷ 남은 시간(하한 시속 20km) |
| V1 | max(0, t1 − s·T). t1 = A→P 경로 시간, T = A→B 경로 시간, s = max(0, d(A,B) − d(P,B)) ÷ d(A,B) |
| V2 (지금 엔진) | 2 × V1 |
| V3 | max(V0, V2) |

엔진에서는 t1을 내비게이션의 `requestTrip()`(경로 안내를 바꾸지 않고 그 지점까지의 거리·도착 예상을 돌려줌)으로 받습니다. 여기서는 OSRM의 A→P 경로 시간을 대신 썼습니다.

## 순서

1. 개발용 12건(시내 4, 국도 3, 해안 1, 산지 2, 고속도로 2)으로 V0를 쟀습니다(`route_check.py`). 경로 가까이 있는 찜일수록 V0가 0에 가깝게 잡혀 9건이 반올림해 0분(분을 빼고 묻는 경우)이었습니다. 그 9건 가운데 5건(C1·C2·C4·R1·R3)은 실제로 2.37~10.13분 더 걸렸고, 4건(C3·S1·M1·M2)은 실제로도 2분 안이었습니다. 12건 가운데 가장 짧게 잡은 것은 H2로, 실제보다 17.7분 짧았습니다(H2는 "약 1분"으로 묻는 경우). 이 단계에서 찜 3곳(M1, H1, H2)은 붙은 길이 차로 들르는 길이 아니거나 공공장소로 보기 어려워 바꿔 다시 쟀습니다.
2. 그 결과를 본 뒤 V1~V3와 채택 기준을 정했습니다.
3. 수도권 밖에서 검증용 경우를 골랐습니다. 먼저 후보 기준 경로(출발→목적지) 22개와 후보 찜의 도로 붙임 22곳을 받았고, 그 가운데 검증용 8건(시내 2, 국도 2, 해안 1, 산지 1, 고속도로 2)과 예비 2건을 골라 `followup.py`에 적고 쟀습니다. 고르는 동안에는 지금 위치에서 목적지·찜으로 가는 경로를 받지 않았으므로, V1~V3와 실제 추가 시간은 고른 뒤에야 계산할 수 있었습니다. 찜이 길에서 200m 넘게 떨어진 경우는 없어 예비 2건은 쓰지 않았습니다. 고른 과정은 아래 "검증용 경우를 고른 과정"에 적었습니다.

채택 기준(검증용 8건): ① 반올림해 0분으로 잡았는데(분을 빼고 묻는 경우) 실제 2분 이상인 경우 0건, ② 고속도로를 빼고 실제보다 짧게 잡은 최대 차이 5분 이하, ③ 허용 10분 판정이 실제와 갈리는 경우 1건 이하. 셋을 모두 채우는 식 가운데 가장 단순한 것을 쓰기로 했습니다.

### 검증용 경우를 고른 과정

고른 기준은 따로 적어 두지 않았습니다. `raw/`의 받은 시각(`fetched_utc`)으로 확인되는 것은 아래와 같습니다. 경로마다 그 바로 뒤에 받은 찜 붙임을 짝지어 보았습니다(`raw_audit.py`, 출력은 `raw_audit_out.txt`).

- 후보는 2026-11-14 03:21:12Z~03:24:50Z에 받았습니다: 기준 경로 22개(검증용 8, 예비 2, 쓰지 않음 12)와 찜 붙임 22곳(검증용 8, 예비 2, 쓰지 않음 12). 지금 위치에서 받는 경로(A→B, A→P→B)는 하나도 없고, 그 요청은 03:27:00Z부터입니다.
- 쓰지 않은 기준 경로 12개 가운데 8개는, 바로 뒤에 받은 찜이 그 경로에서 1.9km 안으로 들어오지 않았습니다(03:21:12·17·21·43·47·52Z, 03:24:05·48Z).
- 03:24:11Z 경로는 NH2와 출발·목적지가 뒤바뀐 경로입니다. NH2는 03:24:46Z에 반대 방향으로 다시 받은 경로를 썼습니다.
- 03:21:29Z와 03:23:39Z 경로는 바로 뒤의 찜이 1.9km 안을 지나는데도 쓰지 않았고, 03:23:34Z 경로는 찜 붙임 없이 받았습니다. 이 셋을 쓰지 않은 이유는 기록이 없습니다.
- NC1(경주 대릉원)의 찜 붙임은 03:21:47Z 경로 바로 뒤에 받았는데, 그 경로는 찜에서 4.08km 떨어져 지납니다. NC1은 03:23:36Z에 분황로에서 출발하는 경로를 새로 받아 썼습니다.
- NM1(성삼재)은 처음 받은 찜 자리(03:23:58Z, 길에서 216m)를 쓰지 않고, 03:24:00Z에 받은 다른 자리(길에서 5m)를 썼습니다. 쓰지 않은 찜 붙임 12곳 가운데 4곳은 길에서 200m 넘게 떨어져 있었습니다(263·309·216·204m).
- 후보 단계의 요청 가운데 검증용 8건 말고는 지금 `followup.py`로 생기지 않습니다(후보 좌표가 스크립트에 없고, 예비는 검증용 찜이 200m를 넘을 때만 받음). 고르는 데 쓴 실행의 코드·기록은 저장소에 없습니다.

## 정한 것

세 식 모두 기준 ①을 NC2 한 건 때문에 채우지 못했습니다. NC2는 찜까지 가는 3.03분이 그동안 목적지 쪽으로 나아가는 몫(3.18분)보다 작아 0으로 나왔습니다. 미리 정한 대로라면 묻는 말에서 분을 빼야 했지만, 결과를 본 뒤 V2를 쓰기로 정했습니다. 판정(③)이 갈린 경우가 없고, 물을 만한 경우(V2 10분 이하)에서 말하는 값과 실제의 차이가 NC2를 빼면 1.1분 안이었기 때문입니다. NH1은 실제보다 21.9분 길게 잡았지만(차이 −21.90분), 길게 잡으면 묻지 않는 쪽이라 말을 거는 일이 늘지 않습니다.

## 한계

- 검증용이 8건뿐이고, V2의 최소 차이는 NH1 한 건이 정합니다. 고속도로 2건은 둘 다 광주대구고속도로입니다.
- 검증용 8건은 개발용의 경향(나들목으로만 드나드는 길에서 크게 틀림)을 안 상태에서, 후보 22개 가운데 골랐습니다(위 "검증용 경우를 고른 과정"). 어림·실제 값은 고르기 전에 계산하지 않았습니다. `raw/`로 확인되는 것은 V1~V3와 실제 추가 시간에 필요한 경로 요청이 모두 고른 뒤라는 점입니다. V0는 고르는 단계의 자료로도 어림할 수는 있었습니다.
- t1과 실제 추가 시간이 같은 길찾기 엔진에서 나오므로, V1·V2가 맞아 보이는 정도의 일부는 구조에서 옵니다. `requestTrip()`의 시간 값은 API 문서상 초 단위입니다(navi-data 3.0.4 `TripInfo.kt` 9행 "eta … in seconds"). 실차에서 받은 값이 실제 도로 시간과 얼마나 맞는지는 아직 확인하지 않았습니다.
- 교통 정보가 없고, 찜 좌표는 가장 가까운 도로에 붙인 어림입니다. P에서 U턴을 허용했습니다.

## raw/에 있는 응답

`raw/`의 217건은 모두 code가 "Ok"인 응답입니다. 두 스크립트가 쓰는 것은 92건(`route_check.py` 60건, `followup.py` 80건, 겹침 48건)이고, 나머지 125건(3,996,492바이트)은 지금 스크립트가 쓰지 않습니다. 측정 과정의 기록이라 지우지 않았습니다. 묶음은 URL의 특징과 받은 시각으로 가릅니다(`raw_audit.py`).

| 쓰지 않는 묶음 | 건수 | 알아보는 법 | 무엇인가 |
|---|---:|---|---|
| 찜 붙임 number=3 | 48 | `/nearest/`의 `number=3`, 02:55~03:04Z | 지금 `snap_place()`는 `number=5`로 받으므로 만들지 않는 요청 |
| 개발용 기준 경로 중 쓰지 않은 것 | 6 | `overview=full`, 02:55~02:58Z | 개발용 12건을 정하며 받았다가 쓰지 않은 출발·목적지 |
| 경유 요청에 steps가 없는 것 | 12 | 세 점 경로, `continue_straight=false`, `steps` 없음, 03:00~03:01Z | 지금 `route_check.py`의 경유 요청과 같고 `steps=true`만 없는 요청 |

| 구간 속도 보조 분석 | 16 | `annotations=speed`, 03:01~03:06Z | 경로 구간의 속도를 본 보조 분석. 그 코드는 저장소에 없음 |

## 다시 돌리기

Python 3.7 이상(표준 라이브러리만)이면 됩니다. 스크립트는 `raw/`의 응답을 먼저 쓰므로 인터넷 없이 같은 결과가 나옵니다. 표는 UTF-8로 내므로 한국어 Windows에서 파일로 받아도(`> 파일`) 끊기지 않습니다.

```
python route_check.py   # 개발용 12건 → route_check_out.txt와 같은 표, results.json을 다시 씀
python followup.py      # V0~V3 비교 → followup_out.txt와 같은 표, followup_results.json을 다시 씀
python raw_audit.py     # raw/ 분류와 후보 단계 → raw_audit_out.txt와 같은 표(파일을 쓰지 않음)
```

`results.json`에서 어림이 0.05분 미만이라 무한대가 되는 `ratio`·`back_factor`는 `null`로 적습니다(표에는 ∞). `raw/`에 없는 요청은 OSRM 데모 서버에서 받는데, HTTP 오류·연결 실패·JSON이 아닌 응답·code가 "Ok"가 아닌 응답은 `raw/`에 저장하지 않고 그 자리에서 멈춥니다.

엔진과 같은 식인지는 엔진 테스트로 확인할 수 있습니다. `engine/src/test/.../DetourEstimatorTest.kt`는 NC1의 V0(0.029365807208530055분)·V2(2.886730676986467분)와 NH1의 V2(51.45038030785543분)를 1e-9 안에서, NC2의 V2(0)를 그대로 맞추는지 확인합니다. 이 값들은 `followup_results.json`의 값과 같습니다. 나머지 경우의 V0를 엔진으로 따로 돌려 견준 비교(최대 4.6e-11분 차이)는 기록을 저장소에 넣지 않았습니다.
