# 들를까 (deulleulkka)

Pleos Connect 차량용 앱 "들를까"의 판단 엔진과, 에뮬레이터에서 SDK 동작을 확인한 코드입니다.

들를까는 주차 중에 "가 볼 곳"으로 찜해 둔 장소가 가는 길 근처에 있을 때, 운전에 방해되지 않는 순간을 골라 한 번 묻고, 수락하면 내비게이션 경유지로 넣습니다. 이 저장소의 중심은 "지금 물어도 되는가"를 정하는 판단 엔진입니다.

이 저장소는 현대자동차그룹 차량용 앱 개발 공모전 심사를 위해 공개합니다. 라이선스를 붙이지 않았으므로 저작권은 팀에 있고, 다시 쓰려면 먼저 문의해 주세요. 단, `docs/route-check/raw/`는 공개 길찾기 엔진 OSRM이 OpenStreetMap 자료로 계산한 응답이라 팀의 저작물이 아니며, © OpenStreetMap contributors, ODbL(https://www.openstreetmap.org/copyright)을 따릅니다.

> **main의 최신 상태 (2026-11-15 접수 뒤)**: 공모전 심사 기준은 접수 메일에 적은 커밋 `dfe4f87`이고, 그 시점의 코드와 README는 https://github.com/RealieSoft/deulleulkka/tree/dfe4f87095b845b7217193b1b278ecb5ccebf6cb 에 있습니다. 아래 본문은 그 커밋을 설명하는 글입니다. 그 뒤 main에는 통합 앱의 첫 판을 올렸습니다. main으로 빌드하면 본문과 다음이 다릅니다.
>
> - **실행 화면**: 앱 목록의 "들를까"는 내비 확인 화면이 아니라 통합 앱(`MainActivity`)입니다. 확인 화면 5개는 debug 빌드에만 들어갑니다(`app/src/debug/`).
> - **확인 화면 열기**: 패키지가 `app.deulleulkka.probe`로 바뀌어 `adb shell am start -n app.deulleulkka/.probe.LocationProbeActivity`처럼 엽니다(debug 빌드).
> - **테스트**: 엔진 111개에 더해, 묻고 답하는 흐름을 담은 `core/` 모듈의 테스트 48개가 있습니다(`./gradlew :engine:test :core:test`).
> - **로그**: 통합 앱은 logcat에 좌표·장소 이름을 남기지 않습니다(상태와 개수만). 본문의 로그 설명은 debug 빌드의 확인 화면 이야기입니다.
> - **APK와 엔진**: `apk/`의 APK는 아직 심사 기준 커밋의 확인용 앱이고, 통합 앱 APK는 출시 키로 서명해 따로 올립니다. 엔진에는 카드와 말의 분 표기를 맞추는 함수 하나만 더했습니다.

## 구성

| 경로 | 내용 |
|---|---|
| `engine/` | Android에 기대지 않는 순수 Kotlin 판단 엔진 |
| `engine/.../MomentJudge.kt` | 안전 → 자격 → 가치 → 빈도 순서로 보고, 처음 막힌 곳에서 멈춤. 본 것과 결과를 줄마다 남겨 "왜 그때 물었는지" 화면에 그대로 씀. 찜 반경 2km 밖의 찜, 보류한 사이 반경을 벗어났던 찜, 지나친 찜(진행 방향 뒤쪽), 시속 90km 이상의 고속 주행에서는 묻지 않음. 완전히 멈춘 때도 방향지시등이나 (길 안내 중이면) 다음 회전을 읽지 못하면 묻지 않음. 판단을 통과한 찜이 여럿이면 덜 돌아가는 곳부터, 같으면 가까운 곳부터 물음. 진행 방향을 정할 수 없거나 경유지 수를 읽지 못하면 묻지 않음 |
| `engine/.../DetourEstimator.kt` | 우회 시간 어림. 찜까지의 도로 시간(`requestTrip`)에서 찜까지 가는 동안 목적지 쪽으로 나아가는 몫을 빼고 두 배. 그 값이 없거나 거리와 맞지 않으면 묻지 않고 보류함(남은 시간은 남은 거리로 본 평균 속도가 시속 2~200km 밖이거나, 남은 거리가 없으면 목적지까지 직선거리로 본 속도가 시속 2km 아래일 때. 찜까지 도로 시간은 0분이거나 직선거리로 본 속도가 시속 200km를 넘을 때. 초 단위 값이 분으로 들어온 경우 등). 처음 방식(더 가야 하는 직선거리 × 도로 보정값 ÷ 평균 속도)은 비교 기준으로 남겨 두었고 묻는 판단에는 쓰지 않음 |
| `engine/.../RoadFactorCalibrator.kt` | 직선거리로 어림한 경우, 경유지를 넣은 뒤 내비게이션이 다시 계산한 값으로 도로 보정값(출발값 1.3)을 그 차에 맞춤. 최근 10번까지의 가운데값, 1.0~2.5. 처음 방식과 함께 남겨 두었고, 지금은 묻는 판단에 쓰이지 않음 |
| `engine/.../AskHistory.kt` | 묻고 답한 기록("다음에"는 30일 쉼, 답 없이 두 번 닫히면 "다음에"로 봄. 받지 않는 말로 닫히거나, 질문 도중 답했거나, 답할 수 없던 무음 카드가 닫힌 것은 세지 않음)과 이번 이동의 보류·반경 이탈 기록(판단 결과와 영역 이탈 알림을 어느 순서로 남겨도 같음). 기기 안에만 둠 |
| `engine/.../replay/` | 시나리오 재생기. 출력은 `docs/replay-output.txt`. 마지막 장면은 공개 길찾기로 잰 경우 하나(`docs/route-check`의 NC1, 경주 대릉원)의 좌표와 경로 시간을 그대로 넣어, 엔진의 어림과 같은 지점의 실제 추가 시간을 나란히 적음 |
| `app/` | Pleos Connect 에뮬레이터에서 SDK를 확인한 **확인용 앱**(완성 앱 아님): 내비게이션(NaviHelper 3.0.5), 위치(FusedLocation 1.1.3), 음성(TextToSpeech·SpeechToText 3.3.1), 차량 신호(Vehicle 2.3.2), 확인 영상용 화면. 판단 엔진은 아직 연결하지 않았음 |
| `docs/emulator-check.mp4` | 에뮬레이터 확인 영상(90초, 소리 없음). 칸 나누기, 경유지 넣기, 음성 질문, 녹음한 대답의 인식, 방향지시등 신호. 화면은 `app/`의 `DemoProbeActivity` |
| `docs/emulator-check-1.mp4` | 첫 확인 영상(87초, 소리 없음). 위치 이동과 영역 진입·이탈 알림이 들어 있음. 화면에 "확인용" 표시가 없고, 이 영상의 화면 코드는 저장소에 넣지 않았음 |
| `docs/route-check/` | 우회 시간 어림을 공개 길찾기 경로 20건과 비교한 스크립트·길찾기 응답·결과 |
| `docs/rule-removal-check/` | 묻지 않게 하는 규칙을 하나씩 지운 사본에서 그 규칙의 검사가 실패하는지 확인하는 스크립트와 결과 |
| `apk/RealizeSoft_deulleulkka_release.apk` | 확인용 앱의 release 빌드(아래 "APK") |

## 테스트 환경

- Pleos Connect Emulator v2.1.0, 시스템 이미지 API 34(Android Automotive, 42dot)
- 화면 2560×1440, 160dpi. 앱 영역을 둘로 나눠 내비게이션 옆 칸에 띄워 확인했습니다. 확인 영상은 1920×1080으로 녹화했습니다.
- JDK 17, Gradle 8.10.2(wrapper), Kotlin 2.0, minSdk 28
- 차량 신호는 Pleos Connect Virtual Console로 바꿨고, 위치는 `adb emu geo fix`로 옮겼습니다.

위 에뮬레이터 판과 화면 설정을 보여 주는 기록(설정 화면, 로그)은 저장소에 없습니다.

## 실행

JDK 17이 필요합니다(Gradle이 JDK 17을 찾으므로 JDK 21만 있으면 멈춥니다). 엔진 테스트와 재생기는 Android SDK 없이 돌아갑니다. `app/`을 빌드할 때만 Android SDK(`ANDROID_HOME` 또는 `local.properties`의 `sdk.dir`)가 필요하고, Pleos Connect SDK는 `settings.gradle.kts`에 적힌 저장소에서 받습니다. Windows에서는 저장소 경로에 한글 등 ASCII가 아닌 글자가 있으면 Android Gradle 플러그인이 빌드를 멈추므로 영문 경로에 두세요. 엔진 테스트만 돌릴 때도 같습니다(설정이 `app/`을 함께 읽기 때문). 처음 돌릴 때는 Gradle과 라이브러리를 내려받으므로 인터넷이 필요합니다.

```
./gradlew :engine:test        # 테스트 111개
./gradlew :engine:run         # 시나리오 재생(한국어 Windows 콘솔에서는 출력이 CP949로 나옴. 같은 내용이 docs/replay-output.txt)
./gradlew :app:assembleDebug  # 확인용 앱(Android SDK 필요)
python docs/rule-removal-check/rule_removal_check.py --jobs 4   # 규칙을 하나씩 지운 사본에서 검사 실패 확인(JDK 17, Python 3.9 이상)
```

테스트 111개 가운데 97개는 단위 테스트이고, 14개는 [kotest-property](https://github.com/kotest/kotest)(테스트 전용)로 무작위 상황 1만 개씩에서 성질을 확인합니다. 단위 테스트는 판단 표와 그 경계값(판단 반경 2km, 회전까지 30초·최소 500m, 나들목 1.5km, 멈춘 때 100m, 멈춘 때 찜까지 300m, 90°, 시간 값을 믿는 평균 속도 시속 2~200km, 허용 10분·5분, 0.5분 미만은 분을 빼고 묻기), 시나리오 A·C·D, 응답 기록, 우회 어림, 근거 문구와, 읽은 값이 이상할 때(속도·도로 시간의 NaN·무한대·음수, 후진하면 오는 음수 속도, 거리와 맞지 않는 시간, 방향을 정할 수 없는 좌표, 음수 경유지 수)를 옮겼습니다.

111개 가운데 15개는 묻는 판단에 쓰이지 않는 코드, 곧 남겨 둔 처음 방식(직선거리 어림)과 도로 보정값 맞추기를 검사합니다: `RoadFactorCalibratorTest` 7개(보류 판단을 보는 마지막 1개는 빼고), `DetourEstimatorTest` 6개(직선거리 어림과 평균 속도. 그 가운데 2개는 도로 시간을 쓰지 않는 조건도 함께 봄), 속성 검사 2개(아래 목록의 끝 두 개). 나머지 96개가 판단 규칙과 지금 쓰는 어림·기록을 검사합니다.

무작위 상황에서 확인하는 성질 14개:

- 목적지가 회사면 다른 값이 무엇이든 묻지 않는다
- 통화 중이거나 안내 음성이 나오면 말을 걸지 않는다
- 확인할 수 없는 안전 신호(방향지시등, 브레이크, 통화·안내 음성, 단속 카메라·주의 지점, 길 안내 중의 다음 회전과 그 종류)가 하나라도 있으면 완전히 멈춘 때만 묻는다
- 이미 경유지가 있거나 잔량이 기준 아래면 묻지 않는다
- 진행 방향 뒤쪽의 찜(이미 지나친 곳)은 묻지 않는다
- 시속 90km 이상이면 묻지 않는다
- 속도·찜까지 도로 시간·남은 시간이 NaN·무한대·음수면 읽지 못한 것과 같아 묻지 않고, 물을 때의 우회 시간으로는 늘 묻는 말을 만들 수 있다
- 찜이 판단 반경 2km 밖이면 묻지 않는다
- 보류한 사이 반경을 벗어난 찜은 그 이동에서는 묻지 않는다
- 처음 막힌 곳에서 멈추고 그 뒤 항목은 보지 않는다(안전 단계를 지나 뒤 단계에서 막히는 경우가 충분히 나오는지도 셈)
- 답 없이 닫힌 횟수는 어떤 순서로 답해도 두 번 이상 남지 않는다
- (검사가 비어 있지 않은지) 묻기 좋은 순간을 만드는 생성기에서는 묻는 경우가 충분히 나온다
- (처음 방식) 보정값이 커지면 직선거리 어림도 커지거나 같다
- (처음 방식) 보정값은 어떤 기록이 쌓여도 상한과 하한을 벗어나지 않는다

안전 규칙 검사는 "다른 조건은 모두 묻기 좋고 찜은 2km 안 아무 방향"인 순간에서 규칙 하나만 바꿔 봅니다. 모든 값을 무작위로 두면 묻는 경우가 거의 나오지 않아 규칙이 빠져도 통과하기 때문입니다. 묻지 않게 하는 규칙 8가지(통화·안내 음성, 확인할 수 없는 안전 신호, 회사 가는 길, 이미 있는 경유지, 낮은 잔량, 지나친 찜, 시속 90km 이상, 판단 반경 밖)와 보류한 사이 반경 이탈, 멈춘 때 읽지 못한 방향지시등·다음 회전을 소스에서 하나씩 지운 사본에서 그 규칙의 검사가 실패하는지는 `docs/rule-removal-check/rule_removal_check.py`로 누구나 다시 돌려 볼 수 있습니다. 마지막으로 돌린 결과는 [`docs/rule-removal-check/result.txt`](docs/rule-removal-check/result.txt)에 있습니다.

`app/`에는 자동 테스트가 없습니다. 엔진 테스트는 SDK 값을 엔진 입력으로 바꾸는 부분을 검사하지 않습니다(그 코드는 아직 없습니다).

## 우회 시간 어림

처음에는 더 가야 하는 직선거리에 도로 보정값을 곱해 평균 속도로 나눴습니다. 공개 길찾기 엔진 OSRM(지도 자료 © OpenStreetMap contributors)의 경로 12건과 비교하니 가는 길에 가까운 찜일수록 0에 가깝게 잡혀, 9건이 반올림해 0분이 되어 분을 빼고 묻게 되었습니다. 그 9건 가운데 5건은 실제로 2분 넘게(가장 크게는 10.1분) 더 걸렸습니다. 12건 가운데 가장 짧게 잡은 것은 고속도로 1건으로, 실제보다 17.7분 짧았습니다. 그래서 찜까지의 도로 시간을 쓰는 식을 정하고, 채택 기준을 먼저 적은 뒤 다른 지역 8건으로 다시 쟀습니다.

- 허용 시간(10분·5분) 판정이 실제와 갈린 경우: 0건
- 물을 만한 5건 가운데 4건: 말하는 값과 실제의 차이 1.1분 안
- 여수 시내 1건: 실제 2.9분 더 걸리는데 반올림해 0분으로 잡음(분을 빼고 물음). 이 1건 때문에 미리 정한 기준("반올림해 0분으로 잡았는데 실제 2분 이상 0건")은 채우지 못했습니다
- 고속도로에서 나들목으로 빠져 되돌아오는 1건: 21.9분 길게 잡음(길게 잡으면 묻지 않는 쪽)

8건뿐이고 교통 정보가 없는 값입니다. 찜까지의 시간과 실제 추가 시간이 같은 엔진에서 나와 실차보다 잘 맞아 보일 수 있습니다. 검증용 8건은 후보 경로 22개 가운데 골랐고, 고른 과정과 자세한 값, 다시 돌리는 법은 [`docs/route-check/`](docs/route-check/)에 있습니다.

찜까지의 도로 시간을 받지 못하면 묻지 않고 보류하고, 값을 받으면 다음 판단에서 다시 봅니다. 처음 방식(직선거리)은 실제보다 크게 짧을 수 있어, 그 값으로 물으면 얼마나 더 걸리는지 모르는 제안이 되기 때문입니다. 처음 방식과 도로 보정값 맞추기는 지우지 않고 남겨 두었습니다. 실차에서 도로 시간을 받지 못하는 일이 잦으면 대안을 다시 견줄 기준으로 씁니다.

### 확인용 앱의 한계

- **녹음한 대답이 없음**: 녹음한 대답 파일(`*.pcm`, 아래)이 APK에 들어 있지 않습니다. 음성 화면의 대답 인식 단계와 확인 영상용 화면의 ④ "대답 인식" 장면은 파일을 찾지 못해 예외로 끝나므로, 영상의 인식 결과("들를게"가 "들을게"로 적히는 것 등)는 APK로 다시 볼 수 없습니다.
- **영상을 그대로 다시 만들 수 없음**: 첫 영상(`emulator-check-1.mp4`)의 화면 코드는 저장소에 없습니다. 둘째 영상(`emulator-check.mp4`)의 칸 나누기와 방향지시등 바꾸기는 공개하지 않은 PC 쪽 녹화 스크립트가 맡았고, 확인 영상용 화면의 시간표는 그 스크립트에 맞춰 두었습니다. 첫 영상의 화면에는 "확인용 앱(시연 앱 아님)" 표시가 없습니다.
- **주행 중에는 쓸 수 없음**: 매니페스트에 주의 분산 최적화(DO) 선언이 없어, Pleos의 주행 규제 정책상 주차 상태에서만 열립니다.
- **화면 멈춤**: `requestRoute()`는 부른 스레드를 약 2초 멈췄습니다. 확인용 앱은 모든 화면에서 이것을 화면(메인) 스레드에서 부르므로, 경로를 정할 때마다 화면이 약 2초 멈춥니다.
- **로그에 위치·장소 이름이 남음**: 확인 기록을 logcat(`DeulleulkkaProbe` 태그)에 그대로 남겨, 위치 좌표와 즐겨찾기·최근 목적지 이름이 시스템 로그에 기록됩니다.
- **쓰지 않는 마이크 권한**: `android.permission.RECORD_AUDIO`를 선언했지만 앱 코드에는 이 권한을 쓰는 곳도, 실행 중 요청도 없습니다. 음성 SDK 문서가 요구하는 권한은 `STT_SERVICE`·`TTS_SERVICE`입니다.
- **생명주기 처리 없음**: 확인 영상용 화면 말고는 칸 크기가 바뀌면 화면이 새로 만들어져, 확인 단계(경로를 바꾸는 단계 포함)가 처음부터 다시 돕니다. 화면이 가려져도 예약한 단계와 차량 값 다시 읽기는 멈추지 않습니다.
- **고정 지연**: SDK가 준비됐다는 콜백을 기다리지 않고 정해 둔 시간 뒤에 다음 단계를 부르며, 일부 실패는 예외 이름만 남기거나 기록하지 않습니다.
- **숨김·지원 종료 예정 API**: 기어는 Vehicle SDK의 숨김 API `getGear()`(지원 종료 예정, SDK가 `GEAR_SELECTION` 속성을 쓰라고 안내)로, 좌석 지원 확인은 지원 종료 예정인 목록형 `checkSeatOccupancyCapabilities`로 읽었습니다.
- **기록과 테스트**: `app/`에는 자동 테스트가 없고, 아래 "확인한 것"의 수치를 뒷받침하는 원본 기록(logcat)은 영상에 담긴 화면 말고는 저장소에 넣지 않았습니다.
- **표시**: 앱 이름이 "들를까"이고 아이콘이 없으며, 앱 목록에서 여는 내비 확인 화면에는 "확인용" 표시가 없습니다.

## 에뮬레이터에서 확인한 것과 한계

확인한 것:

- 내비게이션: 즐겨찾기 읽기, 경유지 넣고 빼기(넣고 6~7초 뒤에 다시 계산된 경로 값을 받음. 두 영상에서 각각 6.5초, 7.1초, 2026-11-15 다른 PC에서 다시 재니 약 6.2초), `requestTrip()`(경로 안내를 바꾸지 않고 그 지점까지의 거리와 도착 예상을 돌려줌. 시간 값은 API 문서상 초 단위로, navi-data 3.0.4 `TripInfo.kt` 9행에 "eta … in seconds"라고 적혀 있음. 에뮬레이터 통신이 끊겼을 때는 실패). `requestRoute()`는 부른 스레드를 약 2초 멈춥니다. 확인용 앱은 이것을 화면 스레드에서 불렀고(위 "확인용 앱의 한계"), 완성 앱에서는 화면 스레드 밖에서 부릅니다.
- 위치: `adb emu geo fix`로 옮긴 위치와 영역 진입·이탈 알림.
- 음성: TTS로 한국어 질문을 말하고, PC로 합성한 대답을 STT `sendAudio()`로 넣어 인식. 온디바이스 인식은 `Locale.KOREA`여야 합니다(`Locale.KOREAN`은 "unsupported locale: ko-"로 거절). TTS의 이벤트 리스너(`addEventListener()`)는 `initialize()` 뒤에 붙입니다(앞에 붙이면 SDK 안에서 lateinit 예외). STT의 리스너(`addListener()`)는 확인용 앱에서 `initialize()` 앞에 붙였고 그대로 동작했습니다. 합성 음성의 "들를게"는 "들을게"로 적혔고, 앱에는 인식기의 첫째 후보만 옵니다. 쉼표가 든 대답은 결과가 둘로 나뉘어 오고, "응, 들를게"는 "응"과 "길게"로 적혔습니다.
- 오디오: 내비 안내 음성(`USAGE_ASSISTANCE_NAVIGATION_GUIDANCE`)과 에뮬레이터 전화의 통화 모드가 일반 앱에 보입니다.
- 차량 신호(Vehicle SDK): 방향지시등·브레이크·충전율·기어를 읽고 구독할 수 있고, Virtual Console로 값을 바꿀 수 있습니다. 착좌 값은 콘솔과 반대로 왔습니다. Vehicle 2.3.2 소스는 착좌의 원래 값이 1일 때만 true로 바꿉니다(`SeatImpl.kt` 435행, `PropertyCallback.kt` 352행). AOSP의 좌석 착좌 값은 0 모름, 1 비어 있음, 2 탑승이라, Pleos가 이 값을 그대로 쓴다면 true는 "비어 있음"이고 "모름"과 "탑승"은 둘 다 false로 옵니다(Pleos 쪽 값 대응은 공개되지 않아 확인하지 못했습니다). 그래서 이 API 값만으로는 "모름"을 알 수 없고, 좌석별 지원 확인 API로 가려야 합니다. 속도 API는 없습니다.
- 창: 새 앱은 왼쪽 칸에 열리고 오른쪽 칸 앱이 잠시 빠집니다. 칸 크기가 바뀌면 화면이 새로 만들어집니다. 가려진 앱은 약 10초 뒤 멈춰, 그동안의 차량 콜백을 다시 보일 때 한꺼번에 받습니다. 나눠 띄운 뒤 다른 앱을 열었다 닫으면 원래 배치로 돌아오고, 모의 절전(`cmd car_service suspend --simulate`)에서 깨어난 뒤에도 배치가 남았습니다. 방향지시등을 켜면 시스템 카메라 창이 왼쪽 칸 위쪽 자리에 뜹니다(칸이 아니라 화면 자리).

위 관찰 가운데 영상에 담긴 장면 말고는 원본 기록(logcat)을 저장소에 넣지 않았습니다.

한계:

- 마이크로 말한 대답과 블루투스 휴대폰 통화는 확인하지 못했습니다. 재부팅 뒤에 나눠 띄운 창이 남지 않는 것은 확인했고, 실차의 시동 끄기가 재부팅과 같은지는 모릅니다.
- 에뮬레이터 내비게이션의 경로 값은 실제 도로 값이 아니어서, 도로 보정값 맞추기는 단위 테스트로만 확인했습니다.
- 영상의 카메라 창 안에 나오는 에뮬레이터 견본 영상은 흐리게 가렸습니다.
